# Fidelity

What each twin models, how closely, and whether it has been checked against the real service.

**Modeled** means it behaves like the public docs describe. **Approximate** means the shape is right but details differ. **Not yet** means calls fail clearly instead of returning wrong data.

Scenarios can make the two twins disagree on purpose (`world.drift`: respelled customers, customers in only one system, customers the books made inactive who have paid for new work since), the way real businesses' systems drift.

**Verified** means checked against a live vendor sandbox, with the date. The [conformance suite](conformance/README.md) does the checking: it records what a real sandbox does for the rows marked "check" and fails a test wherever the twin differs. Nothing has been recorded yet, so everything is built from public documentation and marked "docs only". Anything marked "check" is our best reading of the docs and should be confirmed first.

Each POST carries one event: Intuit may put several in one array (for several companies), so read every element. Only 200 counts as an answer, as the docs word it. The twin gives up after 20 attempts (about three days); Intuit doesn't say when it stops. Deliveries go out right after the change, though Intuit says the first "may take up to five minutes". Each URL gets its deliveries one at a time, in order, and different URLs don't wait for each other. Intuit may hold back later events until a failing one is answered, and notifies only apps connected to the company by OAuth; the twin does neither |

| Webhook details the docs don't give | Approximate | check | Jobber assigns each app a UUID `appId`; the twin derives one from the client_id. Apps have 1 second to answer (documented); a delivery that isn't accepted is tried up to 5 times, 1, 2, 3, then 4 minutes of twin time apart: the docs promise at-least-once delivery without a schedule. Each URL gets its deliveries one at a time, in order, and different URLs don't wait for each other. Jobber may disable webhooks that keep failing; the twin doesn't. The docs' sample signature matches neither sample secret, so the twin follows the documented algorithm |
| Duplicate, late, and out-of-order deliveries | Via faults | | Fault rules with `webhook: TOPIC` (or `"*"`) and `effect: { duplicate: true }` or `{ delayMs }`. Jobber documents duplicates ("the same webhook may be delivered more than once"); late deliveries arrive after later ones |
| Other webhook topics, `APP_CONNECT`, `APP_DISCONNECT` | Not yet | | `WebHookTopicEnum` isn't public, so the twin only sends the topics the docs name and it has events for |
| OAuth 2.0 authorization (`GET /api/oauth/authorize`) | Modeled | docs only | Approved at once and redirected back with `code` and `state`. PKCE with S256 only, as documented |
| OAuth 2.0 tokens (`POST /api/oauth/token`) | Modeled | docs only | Client credentials in the form body; `authorization_code` (with `code_verifier` when PKCE was used; a wrong one is 400 `invalid_grant`, as documented) and `refresh_token` grants; `{ access_token, refresh_token, token_type: "Bearer", expires_in: 3600 }`. Access tokens are HS256 JWTs whose payload carries `exp`. Codes last 10 minutes and work once. A `redirect_uri` that isn't an absolute URL, and a token request that isn't form-encoded, answer 400 `invalid_request` |
| Refresh token rotation | Modeled | docs only | On, as for apps created after January 2, 2024: each refresh returns a new refresh token and the old one fails at once with "The provided refresh token is not valid." The pre-2024 warning behavior and rotation-off mode are not modeled |
| Expired or unknown token on the API | Approximate | check | In `auth: oauth` mode, 401 `{ "message": "Invalid Token Error" }`. The docs name the error but don't show the body. Any `client_id` and `client_secret` are accepted; scopes are not enforced |
| Cost budget per app | Modeled | docs only | Every token issued to one `client_id` shares one budget, so refreshing doesn't refill it. In any-token mode an unknown token counts as its own app |
